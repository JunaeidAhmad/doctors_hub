# API Versioning — Doctor's Hub

This document is the versioning contract between the backend and its clients.
It is written primarily for the **Flutter patient app** developer; the backend
half (policy, freeze checklist, v2 playbook) follows at the end.

Related files:

- `docs/api/openapi.v1.json` — **source of truth** for the v1 contract. Dart
  models may be generated from it.
- `docs/api/CHANGELOG.md` — contract changes, newest first.
- `core/api_contract.py` — the machine-readable surface list.

---

## For the Flutter developer

### Base URL and headers

Base URL: **`/api/v1`**. Every request goes under it — e.g.
`GET https://api.example.com/api/v1/doctors/`.

Send on **every** request:

| Header | Value | When |
| --- | --- | --- |
| `X-App-Platform` | `android` or `ios` | always |
| `X-App-Build` | the integer build number of the app | always |
| `Authorization` | `Bearer <access_token>` | when logged in |

Without the `X-App-*` headers the server treats the client as anonymous tooling
and never gates it — but your app will then not receive proper update gating.
Invalid header values are treated as absent (never a `400`).

### App start: call app-config first

Before anything else, call `GET /api/app-config/` (unversioned and permanent —
it works even when your API version is retired). It returns (abridged):

```json
{
  "api": {"current_version": "v1", "supported_versions": ["v1"],
          "deprecations": {"v1": {"deprecated_on": null, "sunset_on": null}}},
  "platforms": {
    "android": {"min_supported_build": 0, "latest_build": 0, "store_url": ""},
    "ios":     {"min_supported_build": 0, "latest_build": 0, "store_url": ""}
  },
  "update_message": {"en": "", "bn": ""},
  "client": {"platform": "android", "build": 42, "status": "ok"},
  "server_time": "2026-10-05T10:00:00+06:00"
}
```

What to do with `client.status`:

| `client.status` | Meaning | App behavior |
| --- | --- | --- |
| `ok` | build is current | proceed normally |
| `update_available` | newer build exists | show a dismissible update banner (`update_message`, `store_url`) |
| `update_required` | build is below the supported minimum | block the app on a full-screen update page (`update_message`, `store_url`) — every API call would return 426 |

Also check `api.deprecations.<your version>.sunset_on`: if set, surface a soft
"update soon" notice. The contract of `app-config` itself is **additive-only
forever** — ignore unknown fields.

### 426 Upgrade Required

A `426` response means "update the app", never a bug in your request. Body:

```json
{"code": "app_update_required", "min_supported_build": 10,
 "store_url": "https://play.google.com/…",
 "message": {"en": "Please update", "bn": "…"}}
```

| `code` | Meaning | Screen to show |
| --- | --- | --- |
| `app_update_required` | your build is below the platform minimum | full-screen update page (`store_url`, `message`) |
| `api_version_retired` | the API version you call has been retired | full-screen update page (`update` block has the platform's `min_supported_build`, `latest_build`, `store_url`) |

### Tolerant parsing rules

1. **Ignore unknown fields** in responses — new fields may be added at any time.
2. **Every enum needs an `unknown` fallback** — new enum values may appear in
   responses (that is why response-enum additions are breaking and tracked).
3. **Treat only `required` fields as non-nullable** — optional fields may be
   absent or `null`.
4. Never cache a response across app restarts keyed by URL alone — respect
   `Cache-Control` and re-check `app-config` on start.

### The schema file

`docs/api/openapi.v1.json` is the source of truth for request/response shapes
(including which fields are `required` and `nullable`). Dart models may be
generated from it (e.g. with `openapi-generator` or `dart data_class` tooling).
The live interactive schema is served at `/api/schema/` and Swagger UI at
`/api/docs/` (unversioned; they describe the current version).

## For the backend developer

### What counts as a breaking change (decision D9)

- Removing or renaming a path, method, field or enum value
- Changing a field's type
- A response field becoming nullable or optional
- A request field becoming required
- Adding an enum value to a response field
- Changing a default or meaning

Adding endpoints, response fields, or optional request fields is **not**
breaking. The contract checker (`scripts/check_api_contract.py`) implements
exactly this table.

### Freeze-day checklist (decision D7)

On the day the first Flutter build is published to a store:

1. Add `'v1'` to `API_FROZEN_VERSIONS` in `core/settings.py` (one-line change).
2. Run `python scripts/check_api_contract.py` — it must exit 0.
3. Set `APP_ANDROID_MIN_BUILD` (and `APP_IOS_MIN_BUILD` when applicable) to the
   first store build number in the Render dashboard.

From that day on, any breaking change to the patient surface fails CI until a
v2 is introduced. Until then the v1 snapshot may be regenerated on purpose
(`--update`) when Part 4 fixes v1 shapes.

### The v2 playbook (decision D11)

1. Add `'v2'` to `ALLOWED_VERSIONS` in `REST_FRAMEWORK`.
2. Change only the affected endpoints, at the edge: use
   `core.versioning.VersionedSerializerMixin` (`serializer_classes = {'v2': …}`)
   or per-action `get_serializer_class()` branching on `request.version`.
   Models, services and permissions stay shared. Response caches already
   namespace by version (`core.cache_keys.versioned_key`).
3. Generate `docs/api/openapi.v2.json` (`SchemaGenerator(api_version='v2')`)
   and point the checker at it (it loops `ALLOWED_VERSIONS` automatically).
4. Database changes follow **expand-then-contract**: add nullable columns /
   new tables first, migrate data, only drop/rename after v1 is retired.

### Retiring a version (decision D12)

At most two live versions. A version is retired no sooner than **6 months**
after its successor ships, and only after usage logs (`api.usage` logger) show
its traffic is negligible. The sequence:

1. **Deprecate** — set `API_DEPRECATIONS` (e.g. `v1=2027-06-01`); clients start
   receiving `Deprecation` headers.
2. **Sunset** — set `API_SUNSETS` for the same key; clients receive `Sunset`.
3. **Retire** — remove the version from `ALLOWED_VERSIONS` and add it to
   `API_RETIRED_VERSIONS`. Requests get `426 api_version_retired` (not `404`),
   so old apps can show their update screen.

The legacy unversioned `/api/` alias is retired separately via
`API_DEPRECATE_LEGACY` + `API_DEPRECATIONS['legacy']` / `API_SUNSETS['legacy']`;
it emits `Deprecation`, `Sunset` and a `Link: rel="successor-version"` pointing
at the same path under `/api/v1/`.
